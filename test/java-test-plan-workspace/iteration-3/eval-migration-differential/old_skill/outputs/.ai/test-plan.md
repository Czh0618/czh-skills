# 订单列表查询迁移（MyBatis XML → JPA Specification）测试计划

状态：待评审。评审通过前不写任何实现代码；计划通过后开发不得改动本文件，要改就重新评审。
范围：订单列表查询对外接口不变，内部由 MyBatis XML 手写 SQL 迁到 JPA Specification。属于迁移，走完整流程，必须有差分测试。

## 0. 已确认的前提（来自需求方）
- 生产流量日志含请求参数、响应体、用户身份、租户、时间戳；响应由新代码上线前的老实现产生；已脱敏，不再清洗用户标识。
- 有与日志时点对应的脱敏生产库快照（MySQL）。
- 数据权限在网关，本服务不做数据权限判断。
- Maven 构建；现有测试依赖为 JUnit 5、Mockito（来自需求方描述，未对照 pom 核实，见第 5 节）。
- 新代码作为新版本发布，老版本保留一段时间过渡。
- 回放必须做性能对比。
- 差异由开发负责人裁决；老行为疑似 bug 的先保持一致，后续另拉分支再修。

## 1. 需求拆解
### 1.1 用户流程
- F1 已登录用户（带身份、租户）按条件查询订单列表，含分页与排序，对外契约不变。

### 1.2 验收标准（需求明写）
- A1 对外接口（入参、出参、错误响应）不变。
- A2 新实现对生产流量回放的响应与老实现一致，未批准差异为 0。
- A3 回放同时对比性能：耗时、SQL 条数、是否出现 N+1。
- A4 每条差异由开发负责人裁决；老行为疑似 bug 的，新实现先保持一致并记入台账，后续另拉分支修。

### 1.3 业务规则（需求明写）
- R1 迁移不改变行为：同一请求、同一份数据，新旧输出一致。由差分类场景覆盖。

### 1.4 推导规则（需求没写明，不阻塞评审，由评审人决定是否纳入）
- D1 租户隔离：任何请求的结果只含请求租户的订单。
- D2 分页自洽：各页拼起来等于全量，不重不漏，总数等于实际条数。
- D3 同一请求重复执行，结果（含排序并列项的次序）相同。

## 3. 差分设计与差异裁决
### 3.1 基线
- DIFF-01 的基线是日志里的老响应。DIFF-02、INT-01、INT-02 的基线由老版本在同一份快照上现跑得出。
- 准入前置校验（DIFF-01 开跑前必做）：用老版本在快照上重放一小批日志请求，确认能重现日志里的老响应。重现不了，说明快照与日志对不上，或响应依赖时间、随机数等，此时回放出的差异不能归因于新实现，要先停下来找人。

### 3.2 归一化
- 默认只归一化两项：JSON 字段顺序、空白符。
- 时间格式、浮点精度、列表顺序、空值与缺省字段的区别、服务端生成的字段（请求 ID、服务器时间等）都可能是真实的行为差异，不预先归一化。每新增一条归一化规则，都写进已批准清单，由开发负责人批准后生效。
- 响应里有哪些服务端生成的字段，要看代码和日志样本才知道，见第 5 节。

### 3.3 差异裁决
- 裁决人：开发负责人（用户已指定）。其他人不得裁决，开发不得自己放行。
- 每条差异只有三种结论：
  1. 修新代码，使其与老行为一致；
  2. 接受变化，记入已批准差异清单，写明理由；
  3. 老行为疑似 bug：新实现先保持一致，记入疑似 bug 台账，后续另拉分支再修，本次迁移不顺手修。
- 老行为疑似 bug 的，一律先保持一致，不在迁移分支里修。第 2 种结论只用于确有理由接受变化的情形，由开发负责人明确点头。
- 差异清单字段：差异编号、请求样本（脱敏）、老响应、新响应、差异类别（数据/排序/分页/性能/错误响应）、裁决、裁决人、日期、关联分支或工单。
- 建议用独立文件 .ai/approved-diffs.md 存放已批准差异清单和疑似 bug 台账。计划通过后清单可以增补，但计划本身不改。文件路径和格式待评审确认。
- 通过标准：未裁决差异为 0；结论为“修新代码”的差异全部修完并重跑通过。

### 3.4 回放口径
- 只在测试环境回放，不连生产库；快照和日志都已脱敏，回放过程不再还原用户标识，测试里不打印响应体里的敏感字段。
- 服务时钟固定为日志请求时间戳；老响应若依赖当前时间，这样才可比。
- 回放要走过网关注入身份和租户之后的那一层。具体是请求头、上下文还是别的方式，要看代码，见第 5 节。数据权限在网关，本服务回放不测数据权限。
- 日志里失败的请求（错误响应、超时）也要回放并对比，不只回放成功的。
- 回放报告要统计日志覆盖了哪些租户、哪些过滤条件和排序组合，没覆盖到的交给 DIFF-02 补。

### 3.5 性能对比口径
- 对比对象是同一批请求在老版本、新版本上的耗时、SQL 条数、是否 N+1；同机、同配置、同快照、预热后多轮取中位数，只比相对值，不拿绝对值定通过线。
- SQL 条数新旧用同一口径统计（MySQL 侧状态计数），分页的 count 查询算在内。
- 性能劣化与行为差异走同一个裁决流程，进同一份差异清单，裁决人同样是开发负责人。阈值未定，见第 6 节。

## 5. 待查代码（本次没有目标项目代码，未查证）
本次没有目标项目代码，以下各点都没有查证，计划里涉及它们的地方都是占位或假设。开发前先查清，查到的结论补回本计划并随计划重新评审。

1. pom.xml
   - 现有测试依赖是否只有 JUnit 5 和 Mockito；Spring Boot Test、MySQL 驱动、Hibernate 与 Spring Data JPA 的版本。
   - 是否已经引入 JPA（还是迁移时才加），MyBatis 和 JPA 是否会在过渡期同时存在。
2. 老实现的 MyBatis XML
   - 动态 SQL 里的全部过滤条件及其拼接逻辑（决定 INT-01 的完整清单）。
   - 排序：支持哪些字段、有无默认排序、排序键并列时有没有兜底次序。
   - 分页：用的是 PageHelper 之类的插件还是手写 limit，count 查询怎么写，页码从 0 还是从 1 开始，越界页的返回。
   - 有无关联表、子查询、MySQL 专有函数，有无依赖当前时间的条件。
   - 模糊匹配是否转义通配符，字符串比较依赖库的排序规则（大小写）还是代码里处理。
3. 租户与软删除
   - 租户过滤是写在 XML 里，还是靠 MyBatis 拦截器/插件注入。如果是插件注入，迁到 JPA 后不会自动生效，是最容易悄悄改行为的点，要单独核对。
   - 软删除、逻辑删除条件是在 XML 里写死，还是由框架统一加；JPA 侧是否有对应实现。
4. 网关注入的身份与租户
   - 网关把用户身份、租户传给本服务的形式（请求头、上下文对象或别的方式），回放程序要在哪一层注入（见 3.4）。
5. 响应结构
   - DTO/VO 转换层：字段格式（时间、金额、枚举）、有无服务端生成的字段（请求 ID、服务器时间）、空值是输出 null 还是省略字段（决定 3.2 的归一化范围）。
   - 响应是否在组装时调用其他服务或缓存补字段；回放时这些依赖要不要桩。
   - 日志里的响应体是否被截断，或只记录了部分字段。
6. 老版本的可运行基线
   - 过渡期保留的老版本从哪里构建（分支、tag 或制品），能否在测试环境连同一份快照库起来，DIFF-02、INT-01、INT-02 和准入前置校验都靠它。
7. 既有错误码与校验
   - 非法参数时的状态码、错误码、消息格式（决定 INT-02 的预期）。
   - 全局异常处理是否会因框架从 MyBatis 换成 JPA 而改变异常类型和对应的响应。
