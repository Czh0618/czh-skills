# 目的
需求先定验收，再写代码。把需求拆成端到端、属性、差分、单元/集成四类场景，开发完按这张清单逐项对跑，防止 AI 和它自己写的测试以同样的方式误解需求。

# 适用范围
- 新增接口、业务规则、数据计算、迁移/重构：走完整流程。
- 单字段增减、单点 bug 修复、配置或文案调整：只写 1～2 条 UNIT 场景放进 PR 描述，不建计划文件，不走评审门禁。
- 拿不准时按完整流程走。

# 输入
- 需求文档 / 工单，含用户故事和验收标准
- 已确认的接口契约（OpenAPI）、业务规则、数据计算规则
- 涉及的迁移或重构范围（有旧系统/旧实现时必填）
- 用户主流程清单（feature map：从用户视角列功能、路径、预期结果）

# 步骤
1. 先拆需求，不先写代码。把需求拆成用户流程、验收标准、业务规则三类；验收标准模糊、有歧义的，先标出来问人，不猜、不默认。
2. 给每个场景定编号和类型，写进目标项目根目录的 `.ai/test-plan.md`（这是本 skill 约定的路径，目录不存在就创建），格式见下面模板。至少覆盖：每条主流程 1 条端到端、每条核心业务规则 1 条属性或单元测试、有迁移/重构时 1 组差分测试。
3. 按类型分工，不互相替代：
   - 端到端（E2E）：测真实用户流程，如登录、下单、支付、查订单。纯后端项目走 API 级：真实应用 + Testcontainers 真实数据库，用 RestAssured 等 HTTP 客户端走完整接口链路，断言响应和数据库落库；有前端页面时再用 Playwright。Computer Use、Browser Use、Chrome DevTools MCP 只做 Agent 自查和探索性冒烟，不做 CI 硬门禁。
   - 属性（Property）：测“永远不能被打破”的规则，如往返编解码、不变量（余额不能为负）、幂等性（重试/迁移做两次等于做一次）、等价性（优化版等于朴素正确版）。用 jqwik 生成成千上万个输入来证伪，不手写几百个例子。
   - 差分（Differential）：测迁移/重构有没有悄悄改行为。同一批输入同时跑旧系统和新系统，对比输出；输入用随机生成，或脱敏后的生产流量样本（只在测试环境回放）；归一化无关差异（如空白符），维护一份“已批准的差异”清单。旧系统不一定是对的，差异只说明“变了”，要人判断是修新代码还是接受变化。
   - 单元/集成：测边界值、异常路径、权限/校验失败。JUnit 5 + Mockito；核心模块集成测试用 Testcontainers，不 mock 掉要验证的部分。
4. 依赖先查后加：先看 `pom.xml` / `build.gradle*` 里现有的测试依赖（jqwik、Testcontainers、RestAssured、Playwright 等）。缺的写进计划末尾的“需新增依赖”，随计划一起评审，批准前不引入。
5. 测试计划先过人。写完 `.ai/test-plan.md` 后立即停下，把计划发给用户确认（需求方或代码 owner 评审），确认前不写任何实现代码。计划通过后，开发改动不准改计划本身，要改就重新评审。
6. 开发完按顺序对跑：单元/属性 → 集成 → 端到端 → 差分。逐项回填模板里的“测试文件/方法”和“状态”，记录通过/失败和证据（日志、截图、步骤轨迹），附到 PR。
7. 失败先查代码，不改测试。测试 flaky 时查根因，不加 sleep、不重试到过、不删测试；同一检查失败 3 轮后停下来找人。漏掉的场景要补进计划，变成规则，防止下次再漏。

# 场景清单模板（.ai/test-plan.md）
“测试文件/方法”一列评审时可留空，开发时回填，用来保证需求点到场景到测试可追溯。

| 编号 | 需求点 | 场景 | 类型 | 输入 | 预期结果 | 工具 | 测试文件/方法 | 状态 |
|---|---|---|---|---|---|---|---|---|
| E2E-01 | 下单 | 用户下单并支付成功 | E2E | 登录用户，购物车 1 件商品 | 返回支付成功，订单落库，金额正确 | RestAssured + Testcontainers | 开发时回填 | 待跑 |
| PROP-01 | 折扣计算 | 折扣叠加后总价不为负 | Property | 随机订单金额、折扣组合 | 总价 >= 0，且与朴素算法一致 | jqwik | 开发时回填 | 待跑 |
| DIFF-01 | 迁移 | 老查询与新查询结果一致 | Differential | 随机查询条件 + 脱敏流量样本 | 输出一致，已批准差异除外 | 新旧双跑对比 | 开发时回填 | 待跑 |
| UNIT-01 | 库存校验 | 库存不足拒绝下单 | Unit | 库存 0，下单 1 件 | 返回库存不足错误码 | JUnit 5 + Mockito | 开发时回填 | 待跑 |

# 禁止项
- 禁止在适用范围内的需求上，没有测试计划就直接让 AI 写实现；禁止边写代码边补计划来凑数
- 禁止为了让构建通过而删除、弱化已有场景；测试失败先查代码
- 禁止把 Computer Use / Browser Use 的探索结果当成唯一的端到端证据；CI 门禁必须是确定性的端到端
- 禁止用未脱敏的生产数据跑测试；测试里不硬编码密钥、不打印敏感信息

# 完成标准
- `.ai/test-plan.md` 已评审通过，“测试文件/方法”列已全部回填
- 四类场景按需齐全：主流程有端到端，核心规则有属性或单元，迁移/重构有差分
- 验证脚本全绿，测试结果和失败证据附到 PR

# 验证脚本
- 项目根有 `pom.xml` 跑 `mvn verify`；有 `build.gradle` 或 `build.gradle.kts` 跑 `./gradlew check`
