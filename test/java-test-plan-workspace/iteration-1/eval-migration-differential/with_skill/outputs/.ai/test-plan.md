状态：草稿，待评审。评审通过前不写任何实现代码。

## 0. 范围与前提

- 迁移对象：订单列表查询。老实现为 MyBatis XML 手写 SQL，新实现为 JPA Specification，对外接口（路径、入参、出参）不变。
- 老实现已运行 3 年，历史行为没有文档，以老实现的实际输出作为差分基准。老实现不一定正确，差异只说明变了，要人判断修新代码还是接受变化。

- 本计划只定验收，不含实现。

## 2. 历史行为面清单

老 XML 和生产库都没有行为文档。下表是这类查询迁移时最容易悄悄变掉的候选点，来自通用经验，不是对老代码的断言。评审通过后、开发开始前，需对照老 XML 逐条确认或补充；确认不了的，交给第 3 节的随机差分和第 4 节的流量回放去发现。第 3 节每条场景会标注它覆盖的 B 编号。

| 编号 | 行为面 | 要核对的点 |
|---|---|---|
| B1 | 排序 | 默认排序字段与方向；排序值相同时的次序（可能靠主键或索引隐含，没写进 SQL）；传入未知排序字段或方向时的处理；NULL 排在前还是后 |
| B2 | 分页 | 页码从 0 还是 1 起；size 的默认值与上限；total 是否与列表用同一套条件；越界页返回什么；size 为 0、负数或超大时的处理 |
| B3 | 空值与空白 | 条件为 null、空串、纯空白时是被忽略、被当作精确匹配，还是报错（对应 XML 里 if test 的写法） |
| B4 | 字符串匹配 | LIKE 是前缀、后缀还是两端模糊；% 与 _ 是否转义；大小写是否敏感（取决于库的排序规则）；是否 trim |
| B5 | 时间范围 | 区间开闭；只传起或只传止；起大于止；日期是否补时分秒；时区与存储类型 |
| B6 | 状态与枚举 | 多值 IN；空列表；未知枚举值；库里存在但代码枚举里没有的历史状态值 |
| B7 | 数据权限与软删除 | 租户、用户、角色范围的过滤；软删除标记的默认过滤；这些条件写在 SQL、拦截器还是网关 |
| B8 | 联表与去重 | JOIN 一对多造成的重复行；DISTINCT 或 GROUP BY 的使用；左连接下关联字段为空；分页与 total 在重复行下是否偏差 |
| B9 | 返回字段 | 字段映射；null 与空串；金额精度与小数位；时间格式；枚举的序列化值；老响应里有而新响应缺失或多出的字段 |
| B10 | 异常路径 | 非法参数的返回码与消息；超长 IN 列表；数据库异常时的对外表现 |
| B11 | 性能副作用 | SQL 条数（有无 N+1）；一次加载了多少关联实体；大页深翻页的耗时。是否纳入验收取决于 Q8 |
| B12 | 说不清的行为 | 不预设。由随机差分和流量回放发现，每个新发现的差异走第 5 节裁决，并回补进本清单 |

## 4. 生产流量回放方案

目的：发现第 2 节清单之外、没人说得清的历史行为。回放不是拿日志里的历史响应去比新实现，而是把同一批请求在同一份数据上同时打给老、新两套实现，比较两边此刻的输出。Q1～Q4 回答前，本节只是草案。

### 4.1 输入准备

1. 日志只取订单列表查询的读请求，剔除写请求和其他接口。
2. 脱敏在数据进入测试环境之前完成，由日志 owner 执行（见 Q2）。手机号、地址、姓名、订单号、用户标识、令牌、Cookie 等都要处理。同一原值必须映射到同一替换值，否则筛选条件和库里的数据对不上。脱敏后抽查若干条，确认不含敏感信息。
3. 日志文件和脱敏库快照放在仓库之外的受控位置，不提交进仓库，不打印到测试输出，测试代码里不硬编码密钥。
4. 数据优先用与日志同一时段的脱敏库快照（见 Q3）。没有快照时，只能按请求里的筛选值在测试库里反向造数据，覆盖度会下降，回放报告里要注明。
5. 抽样：先按参数形状对请求去重（用了哪些筛选字段、是否排序、页码区间），再分层抽样，避免稀有参数组合被高频请求淹没。样本量待 Q8 回答后确定。

### 4.2 回放执行

- 同一测试环境内，对同一请求先后调用老实现和新实现，二者读同一份数据，回放期间不得有写入。
- 请求里依赖当前时间的参数固定时钟；依赖登录态的，把日志里的用户身份映射到测试用户（见 Q1）。
- 每条请求记录：请求、老响应、新响应、差异、SQL 条数与耗时（是否验收性能见 Q8）。

### 4.3 归一化

只抹平与业务无关的差异：JSON 字段顺序、空白符。以下消费者看得见的差异不抹平，直接算差异：排序次序、金额小数位、时间格式、null 与字段缺失、错误码与消息。

### 4.4 差异分类与裁决

每条差异归入一类：

- 顺序差异：订单集合相同，次序不同
- 总数差异：total 不同
- 内容差异：订单集合不同
- 字段差异：值、精度、格式、缺失或多出
- 异常差异：一边报错一边正常，或错误码、消息不同
- 性能差异：仅在 Q8 纳入验收时

几万条样本不逐条看。先按差异的形状聚类，每类给出一条最小复现请求，再交给裁决人（见 Q7）。裁决结论只有两种：修新代码，或接受变化并登记到第 5 节。老实现的行为不自动视为正确。未裁决的差异按失败处理。

### 4.5 通过标准

- 样本中没有未裁决的差异。
- 第 5 节里每条被接受的差异都有裁决人和理由。
- 回放中新发现的行为回补进第 2 节，并为它增加场景。计划通过评审后，开发改动不准改计划本身，所以回补要重新评审。

### 4.6 回放覆盖不到的地方

- 只覆盖日志时间窗内出现过的请求，没出现过的组合靠 DIFF-01 的随机生成补。
- 日志和快照里没有的数据状态（例如已下线的历史状态值）覆盖不到，靠 UNIT-04 和 DIFF-05 的构造数据补。
- 回放结果不能代替端到端场景。

### 7.3 失败处理

- 失败先查代码，不改测试。测试 flaky 时查根因，不加 sleep、不重试到过、不删测试、不弱化场景。
- 同一检查连续失败 3 轮，停下来找人。
- 差分出现差异不等于缺陷，走第 5 节裁决：修新代码，或接受并登记。
- 开发中发现计划漏掉的场景，补进计划并重新评审，同时把这类遗漏记为规则，防止下次再漏。
