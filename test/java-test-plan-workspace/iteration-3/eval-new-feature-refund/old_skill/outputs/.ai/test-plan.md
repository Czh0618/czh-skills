## 1 需求拆解

### 1.1 用户流程
- F1 部分退款：对已支付未发货订单提交退款（金额小于剩余可退额），渠道回调成功后退款成功，订单状态回写为部分退款态，库存不动，订单仍可继续退款。
- F2 退满：累计成功退款额等于实付，订单状态回写为“已退款”，整单回补库存。
- F3 渠道失败：渠道回调失败，退款记录为“退款失败”。
- F4 重复提交：同一订单、同一金额的退款请求重复提交，第二次起报错，只生效一次。
- 接口：POST /api/orders/{id}/refunds，契约已确认；请求体字段以 OpenAPI 为准（本计划拿不到，见第 5 节）。

### 1.2 验收标准（需求明写）
- AC-1 已支付且未发货的订单可退款，其他订单被拒绝。
- AC-2 单次退款金额不得超过订单实付金额；多次部分退款累计也不得超过。
- AC-3 部分退款后订单还能继续退款。
- AC-4 退款成功后回写订单状态：退满为“已退款”，部分退款用另一个状态值与之区分（具体值未给，见 Q1）。
- AC-5 库存：部分退款不补库存；退满时整单回补。需求原文只写“退款成功后回补库存”，这里按已确认口径取“部分不补、退满整单补”。
- AC-6 同一退款请求（订单加金额相同）重复提交报错，只生效一次。
- AC-7 退款走第三方渠道，结果由异步回调回来；渠道失败记为退款失败。

### 1.3 业务规则（需求明写，场景表“需求点”列引用这里）
- R1 资格：支付字段为已支付，且发货字段为未发货（是两个字段，不是同一个订单状态）。
- R2 单次上限：退款金额 ≤ 订单实付金额。
- R3 累计上限：同一订单成功退款累计 ≤ 订单实付金额。
- R4 状态回写：退满 = “已退款”；部分退款 = 另一状态值（见 Q1）。
- R5 库存回补：仅退满时，整单回补一次。
- R6 重复判定：订单加金额相同即视为同一请求，重复报错。
- R7 渠道异步：退款先受理，由回调落终态；渠道失败落“退款失败”。

### 1.4 推导规则（需求没写，从需求推出来；不阻塞评审，由评审人决定纳入哪些，场景表里标“推导”）
- D1 金额下界与精度：金额必须大于 0，小数位数不超过实付金额的精度。
- D2 并发不超额：多个退款请求同时到达时，累计仍不超过实付（R3 的并发形态）。
- D3 并发重复提交：同一订单同金额的请求同时到达，也只生效一次（R6 的并发形态）。
- D4 回调重复送达：渠道对同一笔退款重复回调，状态只变一次，库存只回补一次。
- D5 一致性：退款记录、订单状态、库存回补要么一起成功，要么一起回滚。
- D6 鉴权：只有订单所属用户或有权限的角色能发起退款。
- D7 回调来源校验：回调接口要验签，伪造回调不能改退款状态。

**Q2 “重复提交”的判定口径**
- 已确认口径是“同一订单加同一金额算同一个退款请求，重复提交报错”。它与“部分退款后可继续退款”有冲突点：实付 100 的订单，先退 50 成功，再合法地退 50，按字面口径第二次会被当成重复。
- 请明确：(a) 与哪些记录比对，只比进行中的、含已成功的，还是全部历史；(b) 有没有时间窗口；(c) 前一笔已“退款失败”后，同金额再提交算重复还是算重试；(d) 重复时的错误码和 HTTP 状态。
- (d) 先查代码里已有的幂等错误码和约定，查不到再请 owner 给。已查：代码不在手边，查不到。
- 影响：E2E-04、UNIT-03、INT-02。

**Q3 “处理中”的退款占不占累计额度**

- 渠道失败后额度是否释放；订单状态是否保持不变（需求只说退款记录记为失败，没说订单状态）。
- 影响：PROP-01、INT-01、E2E-03。

**Q4 回调与渠道异常怎么处理（需求没写）**

- (b) 退款已成功后又收到失败回调（或相反）：以哪个为准。
- (c) 受理时调渠道同步超时或抛异常：退款记录落什么状态，额度是否占用。
- 本期不做的请明说，计划里就不设对应场景，并在第 1 节标为范围外。
- 影响：UNIT-05、UNIT-06；(a) 目前没有对应场景，等答复后再补。

**Q5 退款受理后、回调回来前订单被发货（可后置）**
