## 1. 需求拆解
### 1.1 用户流程
- 订单列表查询：调用方（用户端或运营端，待确认）按条件筛选、排序、分页获取订单列表。
- 对外接口不变：请求参数、响应结构、分页语义、排序、错误码保持原样，只替换内部查询实现。
- 目标项目代码不在手边，入口 Controller、Service、Mapper XML、实体和表结构都查不到。下面凡是具体字段或规则，都需要评审时对照真实代码核实。

### 1.2 验收标准（原文模糊，标出来问人）
- 原话是“对外接口不变”，没说“行为不变”到什么程度：
  - 老实现里那批“自己都说不清”的历史行为，是要原样保留，还是只保留已知、有意的行为？这决定差分中每条差异按“修新代码”还是“接受变化”处理。见问题 Q1。
  - 是否包含非功能行为：响应耗时、慢查询、大页深翻页的表现、对数据库的 SQL 条数（N+1 风险）？见问题 Q5。

### 1.3 业务规则（待从老 XML 抽取，以下仅为类别，不是已核实事实）
| 类别 | 要从老 XML/代码里确认的点 |
|---|---|
| 动态条件 | 每个 `<if>`/`<choose>` 的触发条件：null、空串、空白串、空集合分别怎么处理 |
| 模糊匹配 | like 的通配符是否转义、是前缀/后缀/全模糊、大小写与数据库 collation 依赖 |
| 时间范围 | 起止是闭区间还是半开区间、是否补到当天 23:59:59、时区、起止倒置时的行为 |
| 枚举/多值 | 状态是否 in 多值、非法枚举值是报错还是忽略、状态码与枚举的映射 |
| 排序 | 默认排序字段、方向、同值时的二级排序（决定分页是否稳定）、允许的排序字段白名单 |
| 分页 | 页码从 0 还是 1、pageSize 上限和默认值、越界页、total 的 count 语句是否与列表条件一致 |
| 关联与去重 | 是否 join 明细/用户等表、一对多时是否 distinct 或分组、总数是否因此偏差 |
| 数据范围 | 租户/组织/用户权限过滤、逻辑删除标记、是否在 SQL 里硬编码了过滤 |
| 返回映射 | 字段别名、null 与默认值、金额精度与舍入、日期格式、枚举转文案 |
| 数据库特性 | MySQL 函数、隐式类型转换、NULL 排序位置、`ifnull`/`concat` 等老 SQL 里的方言行为 |


## 2. 待确认问题（阻塞评审）
以下问题回答前，本计划只是草稿。场景里标了 [依赖Qx] 的，答案出来后可能增删或改口径。

**Q1 历史行为的处置原则（最关键）**
老实现里“说不清”的行为，回放出差异时默认怎么处理？候选：A 一律保留，新实现复刻，包括疑似 bug；B 只保留已知有意的行为，不明差异逐条找人判定；C 允许修正明显 bug，但每条都登记进第 5 节。我不替你选。这决定差分的通过口径，以及“已批准差异”清单怎么增长。

**Q2 生产流量日志里有什么，脱敏了吗**
- 日志只有请求参数，还是请求加老实现的响应？
- 是否含用户标识、手机号、token、订单号等敏感字段？是否已脱敏、谁脱的？
- 脱敏会不会改变查询行为？例如手机号被替换成固定串，精确匹配和 like 的行为就会失真。
- 日志时间跨度和条数是多少？是否覆盖低频组合（极端分页、特殊状态、空条件）？覆盖不到的部分，是否接受用随机生成补？
未脱敏的生产数据不能进测试环境，也不能进仓库。脱敏状态没确认前，DIFF 回放场景不能执行。

**Q3 回放时的数据底座**
请求要命中分支，库里得有对应数据。测试库数据从哪来：脱敏后的生产库快照、自己造数据、还是两者结合？数据量级多大？只有请求没有数据时，大部分查询会返回空集，差分形同虚设。

**Q4 新旧能否在同一测试环境里双跑**
迁移完成前，老 MyBatis 实现能否保留并可被测试调用，作为同一输入下的对照（双跑）？还是只能拿日志里记录的老响应当基准（golden）？后者要求数据快照和日志产生时刻一致，否则差异分不清是行为变了还是数据变了。两种方案的取舍见第 4 节，请选。

**Q5 非功能行为是否纳入验收**
响应耗时、SQL 条数（N+1）、深翻页和大结果集的表现，要验收，还是只验功能行为？JPA Specification 在 join 和 fetch 上很容易和老 SQL 的执行计划不一样，这条不问清，事后才暴露。

**Q6 接口范围和调用方**
本次迁移涉及几个入口（用户端、运营端、导出、内部服务调用）？“对外接口不变”覆盖哪些调用方？是否知道有调用方依赖未文档化的行为，如排序稳定性、total 口径、空参数的默认值？

**Q7 时间相关条件**
查询是否含“近 N 天”之类相对当前时间的条件？回放时是否需要固定时钟，日志里的时间戳以什么为基准？

**Q8 谁拍板差异**
“已批准差异”由谁批准（需求方还是代码 owner）？回放差异很多时，是否同意按差异类型归并后分批评审，而不是逐条看？

## 4. 差分方案细则
### 4.1 比对基准二选一（Q4 未答前不定）
| | A 新旧双跑 | B golden 比对 |
|---|---|---|
| 做法 | 同一数据快照、同一请求，同时调老 MyBatis 实现和新 JPA 实现 | 用日志里记录的老响应当基准，只跑新实现 |
| 前提 | 迁移期间老实现保留，且测试里可调用 | 日志含老响应，数据快照与日志产生时刻一致 |
| 风险 | 两套实现在同一测试里共存的维护成本 | 数据漂移会造成假差异；随机输入没有老响应，DIFF-02 到 DIFF-10 的随机部分跑不了，只能靠日志 |

### 4.2 回放流程（两种方案通用）
1. 只取日志中的只读查询请求，剔除写接口，确认回放无副作用。
2. 脱敏确认先于回放（Q2）。未确认脱敏的日志不进测试环境，不进仓库。

### 4.3 归一化红线
- 只允许：JSON 字段顺序、空白符、每次必变的字段（追踪 id、服务端生成的时间戳）。
- 不归一化：列表顺序（排序是要验的行为）、金额精度、null 与缺省字段、日期格式。
- 不许为了让差异变 0 而加规则。新增归一化规则要写明理由，重新评审。

### 4.4 差异分类与处理
| 类别 | 处理 |
|---|---|
| 新实现 bug | 改新代码，不改本计划 |
| 老实现的疑似 bug | 按 Q1 口径：A 则新实现复刻；C 则逐条登记第 5 节 |
| 数据或环境造成 | 修数据底座后重跑，不登记为已批准差异 |
| 无法判断 | 停下找人（Q8），不默认接受 |

同一差异连续 3 轮修不掉，停下找人。已批准差异只增不悄悄删，每条要有批准人和日期。

### 4.5 数据底座要求（Q3）
- 数据库类型、版本、字符集、collation、sql_mode 与生产一致。like 大小写和排序规则依赖这些，不一致会产生假差异或漏掉真差异。
- 数据覆盖流量里出现过的各类状态，加上多租户、逻辑删除、一对多明细、并列排序键、边界时间。
- 数据量要够大。小数据上 JPA 和 XML 常常一样，去重、深翻页、total 的差异要在大数据上才暴露。具体量级待 Q3。
