## 1. 需求拆解

### 1.1 用户流程
- F1 对已支付未发货订单发起部分退款，渠道回调成功，退款生效
- F2 同一订单继续部分退款，累计退满
- F3 渠道回调失败，退款记为退款失败
- F4 同一退款请求重复提交，报错且只生效一次

### 1.2 业务规则（需求和已确认口径里明写的）
- R1 只有已支付且未发货的订单可退款；“已支付未发货”由另一个字段记录，不是订单状态
- R2 单次退款金额不超过订单实付金额
- R3 多次部分退款累计不超过订单实付金额
- R4 部分退款不补库存；累计退满时整单回补库存
- R5 退款成功后回写订单状态：退满为“已退款”；部分退款用与退满不同的状态值（具体值没写明，见 Q1）
- R6 同一退款请求按“订单 + 金额”判断，重复提交报错，只生效一次
- R7 退款走第三方渠道异步回调；渠道失败记为退款失败
- R8 部分退款后仍可继续退款

### 1.3 推导规则（需求没写明，不阻塞评审，由评审人决定是否纳入；金额和并发出错代价高，建议至少纳入 D1、D2）
- D1 并发提交退款时，累计金额同样不超额
- D2 渠道回调重复投递时，库存只回补一次、金额只计一次
- D3 退款金额为空、0、负数时拒绝
- D4 退款记录进入终态（成功或失败）后，不被后到或乱序的回调改写
- D5 回调处理中库存回补失败时，不留下“订单已退款但库存没回补”的半成品
- D6 退款失败时，订单状态和库存保持不变
- D7 只能退自己有权限的订单（数据权限；项目的权限模型查不到）

### 4.2 环境与跑法

- 本机和 CI 都能跑 Docker，满足 Testcontainers 的要求。
- MySQL 镜像版本应与线上一致。线上版本查不到，请告知，或开发时核对后回填。
- 所有场景只在本机或 CI 的 Testcontainers 里跑，不连 dev、test 各环境的 k8s，也不调真实第三方渠道。渠道客户端用测试替身，回调通过 HTTP 打到回调入口模拟。
- 验证命令：项目根有 pom.xml，跑 `mvn verify`。
- 对跑顺序：单元/属性 → 集成 → 端到端。本计划没有差分场景。
- 集成和 E2E 是否被 `mvn verify` 默认执行，取决于项目现有的 surefire/failsafe 配置和测试类命名约定，这里查不到。若现有配置不会执行这两类测试，插件配置和命名约定也算新增项，评审时一并确认。
- Docker 不可用的环境（例如部分 CI 节点）会让集成和 E2E 无法执行，不能以跳过代替通过。
