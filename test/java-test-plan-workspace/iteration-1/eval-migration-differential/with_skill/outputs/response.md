**计划的思路**

这是迁移，核心验收是差分测试。关于你手上的生产流量日志，有一点要先说清：回放不能拿日志里记录的历史响应去比新实现，因为订单数据早就变了，比出来的差异说明不了问题。正确做法是同一批请求、同一份数据，同时打给老 MyBatis 实现和新 JPA 实现，比较两边此刻的输出。所以老实现要在迁移期间留在同一分支里，直到差分通过。

计划共 7 节：

- 第 1 节：9 个待你确认的问题（见下）
- 第 2 节：历史行为面清单 B1～B12，覆盖排序与同值次序、分页与 total、空值空白、LIKE 匹配、时间区间、枚举、数据权限与软删除、联表去重、返回字段、异常路径、性能副作用。这是迁移最容易悄悄变掉的通用候选点，不是对你老 XML 的断言，需要对照 XML 逐条确认
- 第 3 节：18 条场景，其中差分 5、属性 4、端到端 2、单元 7，每条标了覆盖哪些 B 编号
- 第 4 节：流量回放方案，含脱敏、抽样、新旧双跑、归一化、差异分类与裁决、通过标准、覆盖不到的地方
- 第 5 节：已批准差异清单，初始为空，未裁决的差异按失败处理
- 第 6 节：需新增依赖，暂时全标“待核对”
- 第 7 节：对跑顺序和完成标准

**需要你回答的问题（回答前，相关场景的输入或预期标“待定”，我不替你默认）**

1. 日志里记了什么：请求参数、响应体、用户身份、租户、时间戳各有哪些，是否只含订单列表的读请求
2. 日志是否已脱敏，谁脱敏、怎么脱敏。未脱敏的生产数据不能进测试环境
3. 回放对着哪份数据：有没有与日志时间点对应的脱敏库快照，还是在测试库里另造
4. 迁移期间老 MyBatis 实现能否在同一分支里保留并被测试调用
5. 订单列表的完整入参有没有 OpenAPI 或文档；数据权限（租户、用户、角色）写在 SQL 里，还是在拦截器或网关
6. 生产库的类型、版本、字符集、排序规则。Testcontainers 镜像要与它对齐
7. 差异谁来裁决，默认是否“差异一律先当新代码的问题”
8. 性能是否在验收范围内（耗时、SQL 条数、N+1），订单表和日志的量级大概多大
9. 目标项目用 Maven 还是 Gradle，现有测试依赖有哪些

其中 Q2、Q3、Q4、Q7 会直接决定流量回放能不能开跑，建议优先回答。
