## 为什么不改

1. `isGreaterThanOrEqualTo(1)` 恰好放过了这个测试要抓的缺陷。refund 表出现 2 条，就是同一个请求被退了两次；改成 >=1 之后，这种情况会显示为通过，测试从“能发现重复退款”变成“什么都发现不了”。
2. `Thread.sleep` 加 `@RepeatedTest` 重试到过，只是把 1/5 的失败压成“多跑几次总有一次绿”。并发竞态靠 sleep 只会改变时序，不会消除竞态，问题还在，只是不再报红。
3. java-test-plan 的规则：测试失败先查代码，不改测试；flaky 查根因，不加 sleep、不重试到过、不删测试、不弱化断言；同一检查失败 3 轮后停下来找人。加锁、改隔离级别、调测试数据已经是三轮，这里该停，而不是第四轮继续改症状。
4. 这个失败很可能不是测试不稳，而是真实的并发幂等缺陷：约每 5 次出现 1 次重复退款记录。放到线上就是重复退钱。

## 根因方向（等上面的文件来证实或推翻）

- 判重靠应用层先查后插，两个并发事务都看不到对方未提交的记录；加的锁如果在事务提交前就释放，或者多实例、多连接下锁不共享，仍然会双写。
- 数据库层没有对幂等键的唯一约束兜底。只靠应用层加锁、调隔离级别，原理上挡不住所有并发窗口，这也解释了为什么改了三轮还是偶发。
- 两个“同一个”请求序列化后其实不一样，算出的幂等键不同，于是各自都当成首次请求处理。

先让它能确定性复现（用屏障让两个线程同时放行，循环多轮），再改代码，而不是调到“碰巧不红”。

## 补进验收场景（单点 bug 修复，走小改动路径，放 PR 描述，不建计划文件）

修复实现交给 dev 或你另行发起，我这边只定验收条件：

- 集成：同一请求并发提交 N 次（N>=2），refund 表恰好 1 条，所有响应指向同一笔退款；断言保持 `isEqualTo(1)`，不放宽。
- UNIT：同一请求串行重复提交，只退一次，返回结果与首次一致。
- UNIT：内容不同的请求得到不同幂等键，各自落库。
- 如果最终加唯一约束：存量重复数据的清理迁移与回滚也要有对应场景。

为什么前三轮漏了：改的都是症状，没有先让并发缺陷稳定复现。新规则：并发类缺陷，先写出能稳定复现的用例，再允许改实现。
