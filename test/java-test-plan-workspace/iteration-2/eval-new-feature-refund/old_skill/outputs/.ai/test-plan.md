# 测试计划：订单部分退款

状态：草稿，待评审（含未决问题，评审通过前不写任何实现代码）
接口：POST /api/orders/{id}/refunds（契约已确认；请求体、响应体、错误码尚未提供）
技术栈：Java 17 / Spring Boot 3 / MyBatis；现有测试依赖仅 JUnit 5、Mockito（来自需求方描述，这里没有 pom.xml 可核对）
适用范围：新增接口加多条业务规则，走完整流程。没有旧实现可对照，不适用差分测试。

## 1. 需求拆解

用户流程
- F1 对已支付未发货的订单发起部分退款，成功后库存回补、订单状态回写。
- F2 同一订单多次部分退款，累计最多退到实付金额。
- F3 同一退款请求重复提交，只生效一次。

业务规则
- R1 仅“已支付且未发货”的订单可退款，其他状态一律拒绝。
- R2 单次退款金额 <= 订单实付金额。
- R3 多次部分退款累计 <= 订单实付金额。
- R4 退款成功后回补库存，并回写订单状态（状态值未定，见 Q1）。
- R5 同一退款请求重复提交只生效一次（怎样算“同一请求”未定，见 Q2）。

验收标准：需求只给了规则，没给可直接断言的具体值（状态值、错误码、幂等标识、库存回补量）。这些列在下面的未决问题里，测试计划不自行决定。

## 2. 未决问题（评审前由需求方或代码 owner 回答）

阻塞项，不回答则对应场景写不出预期结果：
- Q1 退款后订单状态：部分退款后用什么值？累计退满后用什么值？处于“部分退款后”的订单，是否仍算 R1 的“已支付且未发货”（能否继续退）？
- Q2 “同一个退款请求”怎么识别：客户端传的幂等标识（放请求头还是请求体，字段名是什么），还是按订单加金额推断？重复提交时第二次返回什么（原结果、409 还是别的）？
- Q3 库存回补量：请求是否带商品明细（skuId 加数量）？只按金额退时库存怎么回补（按比例、不回补、整单退完才回补）？多次部分退款会不会重复回补同一件商品？
- Q4 错误响应：状态不符、单次超额、累计超额、订单不存在、金额 <= 0，各自的 HTTP 状态码和业务错误码是什么？

非阻塞但要定：
- Q5 “退款成功”指什么：只改本地库和库存，还是要调用支付渠道退款（同步还是异步）？渠道失败或超时怎么处理？涉及渠道时计划要补场景，工作量会变大。
- Q6 “已支付、未发货”在代码里怎么判定（订单状态枚举，还是另有发货标记）？退款和发货同时发生时谁优先？这里没有代码，查不到。
- Q7 谁能调用（订单本人、客服、后台），是否校验订单归属？金额单位和精度（元还是分，小数位数）？

## 5. 执行顺序与优先级

评审门禁（实现代码开始前必须完成）：
1. Q1～Q4 必须由需求方或代码 owner 回答，否则 E2E、UNIT、INT 里标“待 Qn”的预期值无法回填。
2. Q8 和依赖三项（jqwik、Testcontainers、RestAssured 或 TestRestTemplate）需评审批准。未批准的依赖，对应场景暂不能执行，计划里保留，不删。
3. 计划通过后，开发过程中不改计划本身；需要改就重新评审。

对跑顺序（按 skill）：单元/属性（UNIT、PROP）→ 集成（INT）→ 端到端（E2E）→ 差分（本需求不适用，没有旧实现）。

时间紧时的优先级建议（只是排序，不删减场景；任何降级都要评审人明确同意，并记录进计划）：

| 级别 | 场景 | 理由 |
|---|---|---|
| P0 上线前必须绿 | UNIT-01～03、UNIT-05、UNIT-11、UNIT-12；PROP-01、PROP-02；INT-01、INT-02、INT-03；E2E-01、E2E-03、E2E-04 | 这是资金和库存类风险：多退钱、重复退、半成功状态。出了问题要补偿资金，大促期间代价最高 |
| P1 强烈建议 | UNIT-04、UNIT-06～10；PROP-03；INT-04～06；E2E-02、E2E-05～07 | 状态校验、库存回补、并发和发货冲突，出问题通常能事后对账修复，但会产生脏数据 |
| P2 可随后补 | PROP-04、INT-07 | 精度和参数校验，常被前面场景间接覆盖，单独成条主要为可追溯 |

明确不做：差分测试（无旧实现）；Playwright（纯后端接口，无页面）；Computer Use、Browser Use 等探索式冒烟不作为 CI 门禁，也不作为唯一的端到端证据。

数据与安全：测试数据全部构造，不使用生产数据；测试里不硬编码密钥、不打印敏感信息。

完成标准：本计划评审通过；“测试文件/方法”列全部回填；`mvn verify` 全绿；测试结果和失败证据附到 PR。

失败处理：失败先查代码，不改测试；flaky 查根因，不加 sleep、不重试到过、不删测试；同一检查连续失败 3 轮停下来找人。
