# 订单列表查询迁移（MyBatis XML 手写 SQL → JPA Specification）测试计划

> 说明：本计划是在没有目标项目代码的环境下写的。凡标注“查不到”的点，需有代码后先核对，再决定是否调整场景。

## 1. 背景与已确认事实

已确认事实（来自用户，不再重复询问）：

- 迁移内容：订单列表查询由 MyBatis XML 手写 SQL 改为 JPA Specification；对外接口（路径、参数、响应结构）不变。
- 老实现已运行 3 年，存在说不清的历史行为，老实现不一定是对的。
- 生产流量日志：含请求参数、响应体、用户身份、租户、时间戳；响应由新代码上线前的老实现产生；已脱敏，用户标识不再清洗。
- 有与日志时点对应的脱敏生产库快照。
- 数据权限在网关，不在本查询内实现。
- 数据库 MySQL；构建 Maven；现有测试依赖仅 JUnit 5 和 Mockito。
- 新代码作为新版本发布，老版本保留一段时间过渡，差分对着老版本跑。
- 回放要做性能对比。
- 差异由开发负责人裁决；老行为疑似 bug 的先保持一致，后续另拉分支再修。

本计划的边界：

- 不测网关的数据权限本身；但回放必须带上网关透传给应用的身份、租户和数据范围信息（见问题 Q1）。
- 日志只在测试环境回放，回放只读，不对任何生产库写入。
- 本环境没有目标项目代码，计划中依赖代码细节的点一律标“查不到”，汇总在第 3 章 B 组，有代码后先核对再决定场景是否保留。

## 2. 需求拆分

### 2.1 用户流程

- 调用方（含网关透传的用户、租户身份）按条件查询订单列表，得到分页结果。具体的筛选条件、排序字段、分页方式、响应字段：查不到（无代码），列入第 3 章 B 组。

### 2.2 验收标准（需求里明写）

1. 对外接口不变：路径、请求参数、响应结构、错误码与老版本一致。
2. 同一请求、同一库快照下，新版本输出与老版本一致，已批准差异除外。
3. 性能一并对比：耗时、SQL 条数、是否出现 N+1；劣化的判定阈值见 Q4。

### 2.3 业务规则（需求里明写）

- R1 老行为疑似 bug 的，先保持一致，另拉分支再修。
- R2 差异由开发负责人裁决，不默认算新代码的问题。
- R3 数据权限由网关负责，应用侧不重复实现。

### 2.4 推导规则（需求没写明，不阻塞评审，由评审人决定是否纳入）

- D1 租户隔离：任何请求只能看到本租户数据。迁移时最容易在 Specification 里漏掉租户条件；应用层是否自己带租户过滤，查不到，见 B 组。
- D2 分页排序稳定：排序字段值相同时，两个版本翻页不重不漏、顺序一致（含次级排序）。
- D3 MySQL 语义一致：字符串比较的大小写、LIKE 通配与转义、NULL 比较、时间边界（左闭右开、时区）。手写 SQL 与 Specification 生成的 SQL 在这些点上容易有细微差别。
- D4 总数与列表一致：若接口返回总数，总条数与分页内容相符。
- D5 空条件、空结果、超大页码、非法参数的响应与老版本一致。

## 3. 待确认问题

### A 组：需要用户回答（代码里查不到，或属于业务决策）

- Q1 网关数据权限：网关把数据范围（如可见店铺、部门）以什么形式传给应用（请求头、token、改写后的请求参数）？日志里记录的是网关改写前还是改写后的请求，是否包含这部分信息？没有的话，回放只能覆盖不依赖网关数据范围的请求，或需要另行补充。
- Q2 脱敏一致性：日志请求参数里的用户、租户、订单号等标识，与脱敏库快照里是同一套映射吗？如果日志和快照分别脱敏、映射不一致，回放会查不到数据，差分结论无效。
- Q3 数据时点：快照是单一时点吗？日志覆盖多长时间？窗口内订单被新增或修改，会让回放结果与日志里的老响应因数据变化而不同。处理方式有两种：只回放窗口内数据未变化的请求，或以老版本在同一快照上现跑的结果为基线、日志响应只作参考。倾向哪种？
- Q4 性能劣化阈值：耗时、SQL 条数各按什么标准判劣化？例如 SQL 条数不得多于老版本、P95 耗时不得劣于老版本多少百分比。这是业务取舍，计划里不替你定。
- Q5 老版本回放环境：测试环境能否部署老版本并连接同一份快照？能的话，差分基线取老版本现跑结果，性能对比也有老版本基线；不能的话，只能对比日志里的响应，日志里没有老版本的耗时和 SQL 条数，性能对比会缺基线。
- Q6 日志范围：日志只含订单列表查询吗，还是混有其他接口、需要先按接口过滤？全量回放还是抽样，日志量级多大？
- Q7 老版本定位：老版本对应哪个 tag、分支或提交，用于差分基线和 git log 追溯。

## 5. 差分回放方案

### 5.1 对象与基线

- 对象：老版本（Q7 指定的 tag 或提交）和新版本，部署在测试环境，连同一份脱敏库快照（依赖 Q5）。老版本保留过渡期，所以差分直接对着老版本跑，不需要两套实现并存于同一 codebase。
- 基线首选老版本在快照上现跑的结果。日志里的老响应只作参考，并用来发现数据漂移：日志响应与老版本现跑结果不一致的请求，单独列出，不计入新代码的差异（依赖 Q3）。
- 如果 Q5 的答复是测试环境部署不了老版本，退化为只对比日志里的响应，此时性能对比缺基线，需要评审人确认如何处理，计划里不替你定。

### 5.2 输入

- 日志请求（DIFF-01）：按 Q6 过滤到订单列表接口，带上日志里的用户身份、租户，以及 Q1 确认的网关数据范围信息。
- 随机请求（DIFF-02）：补日志没覆盖的条件组合，范围由 B2 里 XML 动态 SQL 的分支决定，有代码后再定。
- 时间：查询里用到当前时间时固定时钟（B6），否则两个版本的结果会因为时间不同而不同。
- 安全：只在测试环境回放，回放只读，每轮回放前把快照恢复到初始状态；日志和快照已脱敏，测试里不硬编码密钥，不打印用户标识。

### 5.3 归一化

- 只归一化与业务无关的差异：JSON 键顺序、空白符、traceId、服务器时间等生成值（具体字段看真实日志样本，见 B7）。
- 每条归一化规则写进清单，随计划评审；不归一化业务字段，不为了让对比通过而放宽规则。
- 排序属于行为，有序结果必须按顺序逐条比较，不能因为顺序不同被归一化掉。

### 5.4 差异的处理

- 每条差异记录：请求特征、老响应、新响应、差异字段、归类。
- 归类只有四种：数据漂移、应归一化、新代码问题、老行为疑似 bug。
- 裁决人是开发负责人。新代码问题改新代码；老行为疑似 bug 的，先把新代码改成与老版本一致，另拉分支再修，并记入待修清单；确认接受的变化，进入「已批准的差异」清单。
- 「已批准的差异」清单初始为空，每条含编号、请求特征、原因、批准人、日期；开发过程中不准自行往清单里加条目，要加就走评审。

### 5.5 性能对比（DIFF-03）

- 同一批请求、同一环境、同一数据量，预热后各跑多轮，取 P50 和 P95。
- SQL 条数和 N+1 在 MySQL 端统计，新旧版本同口径，不看应用日志。
- 劣化阈值见 Q4，Q4 回答前这一项只出数据，不判通过与否。

### 5.6 通过判据

- 在 Q6 确定的回放范围内，未解释的差异为 0，每条差异都已归类并裁决，并且已批准的差异都在清单里。
- 性能对比数据已出，且满足 Q4 的阈值。

## 7. 对跑顺序与完成标准

### 7.1 对跑顺序

实现完成后回到本计划按顺序对跑：单元/属性（UNIT-01、PROP-01/02）→ 集成（INT-01/02）→ 端到端（E2E-01/02）→ 差分（DIFF-01/02/03）。逐项回填“测试文件/方法”和“状态”，把通过或失败的证据（日志、差异报告、性能数据）附到 PR。

### 7.2 失败处理

- 失败先查代码，不改测试，不删、不弱化场景。
- flaky 查根因，不加 sleep，不重试到过；同一检查失败 3 轮后停下来找人。
- 漏掉的场景补回本文件并重新评审，同时记下为什么漏。
- 计划通过评审后，开发过程中不准改计划本身；要改就重新评审。

- 本计划已评审通过，第 3 章 A 组问题已全部有答复，B 组已在有代码后逐条核对，必要时已重新评审。
