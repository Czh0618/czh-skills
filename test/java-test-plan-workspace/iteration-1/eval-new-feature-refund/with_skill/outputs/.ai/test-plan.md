# 测试计划：订单部分退款

状态：草稿，待评审（评审通过前不写任何实现代码）
接口契约（已确认）：POST /api/orders/{id}/refunds。请求体、响应体、错误码尚未提供，见第 2 节。
技术栈：Java 17 / Spring Boot 3 / MyBatis；现有测试依赖仅 JUnit 5 + Mockito。

## 1. 需求拆解

用户流程
- F1 已支付未发货订单发起一次部分退款：退款成功，库存回补，订单状态回写
- F2 同一订单多次部分退款，累计不超过实付金额
- F3 同一退款请求重复提交，只生效一次
- F4 不满足条件的退款被拒绝（订单状态不对、金额超限）

业务规则
- R1 仅“已支付且未发货”的订单可退款
- R2 单次退款金额 <= 订单实付金额
- R3 累计退款金额 <= 订单实付金额
- R4 退款成功后回补库存
- R5 退款成功后回写订单状态（目标值待确认，Q1）
- R6 同一退款请求幂等（“同一”如何判定待确认，Q2）
- R7 由 R3 推出：同一订单并发退款，累计仍不得超限（预期待确认，Q8）

验收标准：需求未给出显式验收标准，以上规则即验收依据。下面问题没有答案前，相关场景的“预期结果”只写已确定的部分。

## 2. 待确认问题（阻塞评审）

- Q1 退款后订单状态：部分退款后、全额退完后分别写什么值？现有状态枚举里有没有可用的，还是要新增？部分退款后订单是否仍可再次退款（R3 暗示可以）？
- Q2 幂等：“同一个退款请求”靠什么判定？客户端传的 requestId / Idempotency-Key（契约没写），还是订单 + 金额 + 原因？重复提交时返回首次结果原样，还是返回错误码？同一 key 但金额不同怎么处理？
- Q3 “实付金额”口径：是否已扣优惠券、是否含运费？累计时，处理中和失败的退款是否占用额度？
- Q4 退款是同步完成，还是调用支付渠道后等回调？“退款成功”以什么为准？渠道失败或超时时，库存和订单状态保持不变还是进入中间态？测试中支付渠道用 fake 替身是否可接受？
- Q5 库存回补粒度：部分退款按金额退，还是按商品行和数量退？按金额退时库存回补多少（全回补、按比例，还是仅全额退完时回补）？请求体是否带商品行和数量？
- Q6 “未发货”如何判定：订单状态字段，还是独立的发货单/物流记录？部分发货的订单能不能退？
- Q7 错误响应：订单不存在、状态不允许、超额、金额 <= 0 或精度非法，各自的 HTTP 状态码与业务错误码。
- Q8 并发：同一订单同时两笔退款、各自不超额但合计超额，预期是一笔成功一笔被拒吗？
- Q9 环境：数据库是 MySQL 吗？CI 能跑 Docker（Testcontainers 的前提）吗？

## 4. 需新增依赖（随计划一起评审，批准前不引入）

现状：pom.xml 里只有 JUnit 5 和 Mockito。版本一律在引入时对照项目的 Spring Boot 3 版本确定；Spring Boot 的依赖管理已覆盖的（Testcontainers、RestAssured、spring-boot-starter-test）沿用其管理版本，不单独写死。

| 依赖 | 用途 | 对应场景 | 评审结论 |
|---|---|---|---|
| Testcontainers（JUnit 5 + 数据库模块，数据库种类按 Q9） | 用真实数据库跑 E2E 和集成测试；并发防超退、幂等唯一约束、事务回滚都依赖真实数据库行为 | E2E-01 到 E2E-08、INT-01 到 INT-05 | 待批准 |
| RestAssured | API 级 E2E，走完整 HTTP 链路并断言响应 | E2E-01 到 E2E-08 | 待批准 |
| jqwik | 属性测试，生成大量输入证伪额度不变量和幂等性 | PROP-01 到 PROP-04 | 待批准 |
| spring-boot-starter-test | 提供 Spring Boot Test 和 MockMvc。先核对 pom 是否已间接引入，已有则不用新增 | INT-01 到 INT-06、E2E-01 到 E2E-08 | 待核对 |

不新增的：
- 并发场景用 JDK 自带的 ExecutorService 和 CountDownLatch，不引入 Awaitility 之类的库。
- 支付渠道的 fake 实现是测试代码，不需要依赖（具体形态等 Q4）。
- 前端页面不在本需求范围，不引入 Playwright。

前提与降级：
- Testcontainers 要求 CI 和本地能跑 Docker（Q9）。不能的话，E2E-06、E2E-07、INT-01 到 INT-04 这些依赖真实数据库行为的场景就没有可信的验证手段。换成内存数据库（如 H2）只能覆盖普通业务路径，并发防超退和幂等唯一约束的结论不能算数，需要评审时明确接受这个降级，并在计划里标注这些场景改为“预发环境手工验证”。
- 不批准 jqwik 的话，PROP-01 到 PROP-04 退化为 JUnit 5 参数化加手写边界例子，只能证明所列例子成立，不能证明规则永远成立。

## 6. 评审门禁与对跑顺序

评审通过前，以下三项都要有结论，缺一不得开始写实现：
1. 第 2 节 Q1 到 Q9 已有答案，场景里“按 Qx”的预期结果已改成具体值。
2. 第 4 节新增依赖已批准或已确定降级方案。
3. 评审人（需求方或代码 owner）确认本计划。

通过后，计划不随开发改动。需要改场景，重新评审。

开发完按顺序对跑，逐项回填“测试文件/方法”和“状态”：
1. 单元和属性：UNIT-01 到 UNIT-13、PROP-01 到 PROP-04
2. 集成：INT-01 到 INT-06
3. 端到端：E2E-01 到 E2E-08
4. 差分：本需求不设

失败的处理：
- 先查代码，不改测试，不删、不弱化场景。
- flaky 的场景查根因，不加 sleep，不重试到过。
- 同一检查连续失败 3 轮，停下来找人。
- 漏掉的场景补进计划，重新评审。

完成标准：“测试文件/方法”列全部回填，`mvn verify` 全绿，通过和失败的证据附到 PR。测试数据只用造的订单，不用生产数据。
