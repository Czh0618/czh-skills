# 重构决策矩阵

本文档定义 Step 2 重构路线图排序时用到的**收益 × 风险 × 成本**三维评分规则。目标是让排序有客观依据，不靠"AI 印象流"。

---

## 三维评分概述

| 维度 | 含义 | 评分范围 |
|------|-----|---------|
| 收益（Benefit） | 本次重构能带来多少价值 | 1（很小）- 5（很大） |
| 风险（Risk） | 本次重构可能搞砸的概率与影响 | 1（很低）- 5（很高） |
| 成本（Cost） | 本次重构需要消耗的资源 | 1（很小）- 5（很大） |

**综合优先级公式**（仅供排序参考，不强求精确）：

```
综合分 = 收益 - 风险 - 成本/2
```

- 综合分 ≥ 2 → **高优先级**（立即做）
- 综合分 0 - 1 → **中优先级**（本次或下次专项做）
- 综合分 < 0 → **低优先级**（暂搁置，等触发再做）

---

## 收益维度（1-5）

> 问题："改了它能解决什么问题？"

| 评分 | 标准 | 示例 |
|------|-----|------|
| 5 | 解锁当前阻塞的功能开发 / 修复严重 bug | 上帝类拆分后才能加新支付方式；贫血模型搬移行为后状态机才能闭合 |
| 4 | 大幅提升可测性或可读性，影响后续多次开发 | Extract Class 将 700 行类拆为 3 个 200 行；引入值对象消除 6 处数据泥团 |
| 3 | 中等提升可读性，影响 1-2 次后续开发 | Extract Method 将长方法拆为 5 个有名字的小方法 |
| 2 | 小幅提升风格质量 | Replace Magic Number 把单处魔法数提为常量 |
| 1 | 风格性改善，几乎不影响功能开发 | Rename 一个内部变量 |

### 收益打分要素

打分时综合考虑这 4 项：

1. **可读性提升**：改后是否更容易看懂？是否减少阅读时间？
2. **可测性提升**：改后是否更容易写单元测试？是否能打破不可测的依赖？
3. **可扩展性提升**：改后是否更容易加新功能？是否符合开闭原则？
4. **是否解锁阻塞**：当前重构是否是某个功能开发的前置条件？

如果 4 项中只命中 1 项 → 1-2 分；命中 2 项 → 3 分；命中 3 项 → 4 分；4 项全中 → 5 分。

---

## 风险维度（1-5）

> 问题："改了它有多大概率搞砸？搞砸了影响多大？"

| 评分 | 标准 | 示例 |
|------|-----|------|
| 5 | 几乎肯定会出问题 / 出问题影响生产 | 改公有 API 但调用方众多；无测试 + 跨模块改动 |
| 4 | 较高概率出现问题，影响范围大 | 改 `@Transactional` 边界；改并发安全的代码（lock、volatile） |
| 3 | 中等风险，需要谨慎 | 跨包改动；改动有测试但覆盖不全；动 Spring 注入关系 |
| 2 | 较低风险，本地可控 | 单类内的方法搬移；测试覆盖良好的内部重构 |
| 1 | 几乎无风险 | 单文件、单方法、有测试保护的 Extract Method |

### 风险打分要素

1. **测试覆盖**：覆盖率高（> 70%）→ 1-2；中等（30-70%）→ 3；低（< 30%）→ 4-5
2. **影响范围**：单方法 → 1；单类 → 2；单模块 → 3；跨模块 → 4；跨服务 → 5
3. **API 变更**：内部 → 1；包内公开 → 2；模块对外 → 3；HTTP / RPC 契约 → 5
4. **并发与事务**：无并发关注 → 1；线程相关 → 4；分布式事务 → 5

**加权规则**：4 项中取最高 + 第二高的均值，向上取整。

---

## 成本维度（1-5）

> 问题："改这个要花多少时间和资源？"

| 评分 | 估算工时 | 示例 |
|------|---------|------|
| 1 | < 30 分钟 | Extract Method 提取一个方法 |
| 2 | 30 分钟 - 2 小时 | 一组 Extract Method + Introduce Parameter Object |
| 3 | 半天（2-4 小时） | Extract Class 拆出一个新类 |
| 4 | 一天（4-8 小时） | 上帝类按职责拆为 3-5 个类 |
| 5 | 多天 | DDD 战术重构 / 跨模块 / 需协调他人 review |

### 成本打分要素

1. **估算工时**：见上表
2. **依赖前置数量**：每多一个前置 +0.5 分
3. **是否需协调他人**：需要其他模块同步改 → +1 分
4. **是否需要新 API 设计**：需要设计公开接口 → +0.5 分

## 示例：完整评分案例

以 SKILL.md 示例的 OrderService 重构为例：

### 案例 1：Extract Method `calculateShipping`

| 维度 | 评分 | 理由 |
|------|-----|-----|
| 收益 | 4 | 长方法减少 25 行，可测性↑，可读性↑，解锁后续 Extract Class（命中 3 项） |
| 风险 | 1 | 单方法、有测试、纯内部 |
| 成本 | 1 | < 30 分钟 |
| **综合** | **4 - 1 - 0.5 = 2.5** | **高优先级** |

### 案例 2：Extract Class `PricingService`

| 维度 | 评分 | 理由 |
|------|-----|-----|
| 收益 | 5 | 解锁加新支付方式，可测性大幅提升，OrderService 瘦身（命中 4 项） |
| 风险 | 3 | 改 Spring 注入关系，跨包，需新建 Bean |
| 成本 | 3 | 半天工作量 + 依赖 4 个前置步骤 |
| **综合** | **5 - 3 - 1.5 = 0.5** | **中优先级**（建议下次专项排期） |

### 案例 3：Rename 内部变量 `data` → `orderItems`

| 维度 | 评分 | 理由 |
|------|-----|-----|
| 收益 | 1 | 仅风格性改善 |
| 风险 | 1 | IDE 重构无风险 |
| 成本 | 1 | < 5 分钟 |
| **综合** | **1 - 1 - 0.5 = -0.5** | **低优先级**（顺手做即可） |

### 案例 4：将 `Order` 改造为充血领域模型

| 维度 | 评分 | 理由 |
|------|-----|-----|
| 收益 | 5 | 状态机收敛、规则下沉到领域、所有调用方受益 |
| 风险 | 4 | 跨多个 Service 改动、可能涉及 ORM 配置、需考虑序列化兼容 |
| 成本 | 5 | 多天工作量 + 需团队达成共识 |
| **综合** | **5 - 4 - 2.5 = -1.5** | **低优先级**（需专项立项，非顺手能做） |

## 排序原则补充

除综合分外，还需考虑：

### 1. 依赖前置

即使综合分高，如果有前置依赖未满足，应排在前置后面：

```
步骤 1（综合分 1.5）：补特征化测试 → 前置，必须先做
步骤 2（综合分 2.5）：Extract Method
步骤 3（综合分 2.0）：Introduce Parameter Object
```

不能因为综合分 2.5 就把 Extract Method 排到补测试前面。

### 2. 小步快跑原则

同等综合分的情况下，**优先做成本 1-2 的小步**：

- 多做几个小步，每步独立 commit，可以分散风险
- 大步（成本 4-5）容易做一半失败要回滚

### 3. 先安全网后重构

测试覆盖低时（风险评分 4-5），必须把"补测试"作为单独步骤排到最前。
不要把"补测试"和"做重构"合并为一个步骤——这样既无法独立验证测试是否正确，也增加回滚难度。

### 4. 先内部后边界

内部重构（不改公有 API）应优先于公有 API 改动：

- 内部重构出问题影响小
- 公有 API 改动需要协调调用方，应攒到一起做并发版

### 5. 高频代码优先

变更频率高的代码（git log 显示近 3 个月被多次修改）应优先重构：

- 收益放大：每次改都受益
- 风险放大：拖延越久受损越多

---

## 评分的常见陷阱

1. **不要给收益打过高分**：除非确实命中"解锁阻塞"，否则收益很少 5 分
2. **不要给风险打过低分**：测试覆盖低或跨模块时，风险至少 3 分
3. **成本不要只看代码量**：协调成本、review 成本、回滚成本都要算
4. **不要因"想做"就给高优先级**：综合分是客观依据，跟个人偏好分开

---

## 与全局规则的关系

本评分体系与 `~/.claude/rules/issue-handling.md` 的"问题处理原则"对齐：

- "问题说明必须具体" → 评分必须有理由列举
- "优化建议要对应明确的结构风险" → 风险评分要明确指出哪条风险
- "未确认前不主动扩大范围" → 综合分低（< 0）的项不主动推动

把评分写进诊断报告与路线图，等于给用户提供了"为什么这么排"的可审计依据。
